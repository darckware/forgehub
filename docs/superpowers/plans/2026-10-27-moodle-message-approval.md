# Moodle actions: human authorization and Messages delivery

Marcelo authorized supporting the three Moodle operations previously blocked, with destructive actions requiring his confirmation through Telegram, a password entry, and selection in batches. He clarified that the resulting execution is sent to the chosen agent via ForgeHub Messages, using the existing executor field, with a user-supplied instruction/prompt. All registered agents must be visible in the executor dropdown; visibility does not grant an agent a Moodle credential.

Use a private ForgeHub form opened through Telegram; the password must never be provided to the agent, logged, sent to MCP, or stored in the browser. Treat the ForgeHub account password as the working assumption until Marcelo chooses otherwise. No password, authorization link or decision may be sent in a test to a real person.

Each Moodle proposal becomes a pending Messages task bound server-side to its immutable request ID, action hash, environment, source profile and exact executor/message fingerprint. A password-gated human-only batch operation verifies each selected current revision before authorizing and dispatching Messages. Agent credentials and ordinary admin approval paths must not bypass that password gate. At execution the MCP must verify/claim the exact human decision from ForgeHub using the executing agent's identity; local CLI approval alone must not authorize destructive calls. Claims are single-use and failures with an uncertain outcome remain blocked for reconciliation, never retried blindly.

The operator sees the target, action, destructive impact, environment, executor and exact prompt prior to confirmation. The UI lists all registered agents; selecting an agent does not provision or elevate its Moodle access, and failures must be explicit. Confirmation is scoped to the selected batch and must not be reusable for other actions. Preserve old non-destructive workflows and unrelated pending tasks. Use isolated synthetic fixtures and real concurrency/auth tests; do not invoke destructive Moodle writes or create real Messages for validation.

Implementation boundaries: Moodle proposal/allowlist in `/root/project/moodle-telegram-approval/mcp-server`; ForgeHub APIs/models/guards in `backend/app`; bulk confirmation and agent selector in existing Pessoal → Tarefas dos agentes. Existing source state and backups must be preserved. No release until both paths, the authenticated Telegram-to-form entry, password validation, expiry, claims, audit, race handling and independent review are complete.
