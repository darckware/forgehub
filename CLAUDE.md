# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this product is

ForgeHub is a control plane for planning, governing, and executing software projects with AI agents: product/version/project registration, pipeline stages with mandatory artifacts and approval gates, planning items (features/bugs/etc.) broken into tasks, task executions by agents, and an audit trail tying every entity back to a product version. It replaces the previous "Hermes Agent Forge" naming throughout the codebase, UI, and docs.

Full domain model and business rules: `docs/PRD.md` (vision, journeys, definition of done) and `docs/SPEC.md` (entities, business rules, acceptance criteria — see especially §6 for the per-domain rule list referenced from model/route docstrings).

Core invariant from the PRD: no feature, bug, task, skill, execution, or artifact may exist without linkage to product, version, project, planning, pipeline, owner, status, audit trail, and validation criteria. Most tables exist to keep that traceability chain unbroken, not just to store data.

## Canonical stack (confirmed, supersedes SPEC.md §2/§3.2)

`docs/SPEC.md` describes a C#/ASP.NET Core + Dapper backend. That is **stale** — the implemented backend stack matches `docs/TECHNOLOGY.md`:

- Backend: Python 3.11, FastAPI, SQLAlchemy (async) + asyncpg, Alembic migrations, OAuth2 password flow + JWT, pytest + httpx for tests.
- Frontend: React 18 + Vite, TypeScript, shadcn/ui (Tailwind + Radix primitives, via `class-variance-authority`/`clsx`/`tailwind-merge`) + Framer Motion, TanStack Query + Zustand, React Hook Form + Zod, Vitest + React Testing Library.
- Datastore: PostgreSQL (pgvector/pg16), shared instance `company_postgres` on port 5433, database `forgehub`, schema `company` (**every** table — models set `MetaData(schema=settings.POSTGRES_SCHEMA)` in `backend/app/db/base.py`, never `public`). ForgeHub does not run its own Postgres container; `database/postgres-company/docker-compose.yml` only re-documents/recreates the externally-managed container definition (see its trailing comment — do not blindly `docker compose up` there without checking config drift, Kanboard's own database depends on the same container). Full topology: `docs/DB_README.md` and `/root/.hermes/foundation/governance/POSTGRESQL_TOPOLOGY.md`. The other instance, `foundation_postgres` (port 5432), is reserved for internal Hermes/Foundation data — never put ForgeHub application data there.
- Integrations already provisioned in `.env`: Postgres connection (`company_postgres:5433/forgehub`).

When implementing, follow `docs/TECHNOLOGY.md` over `docs/SPEC.md` wherever they conflict (backend language/framework, directory layout). `docs/SPEC.md` remains the source of truth for the domain model, business rules, and acceptance criteria — only its tech-stack sections (§2, §3.2) and its directory layout (§10) are superseded.

## Commands

All commands assume `.env` at the repo root (Postgres credentials) is present.

**Fast iteration (recommended day-to-day — no Docker rebuild per change):**
```bash
./dev.sh            # backend :8001 (uvicorn --reload) + frontend :5173 (vite dev, hot-reload)
./dev.sh status       # what's currently up
./dev.sh stop         # stop both
./dev.sh restart      # stop + start
```
Deliberately on different ports than the Docker deploy (8000/4173) so both can run at once.
Auto-checks `.env`/`backend/.venv`/`frontend/node_modules` and creates/installs what's missing.
Won't kill a process it didn't start; stop targets whoever's actually listening on the port
(`lsof -tiTCP:<port> -sTCP:LISTEN`), not a captured PID — `uvicorn --reload` and `npm run dev`'s
wrapper both fork workers with a different pid than `$!` captures. Use this for verification
(pytest/tsc still apply); only run the Docker command below when a deploy is actually requested.

**Run the full stack (Docker) — only when a deploy is explicitly requested:**
```bash
docker compose up -d --build
curl http://localhost:8000/health        # → {"status":"ok"}
open http://localhost:4173               # frontend (served via `serve`, built dist)
```

**Backend, local dev (manual, if not using dev.sh):**
```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

**Backend migrations (Alembic, async, schema `company`):**
```bash
cd backend
alembic upgrade head
alembic revision --autogenerate -m "<message>"   # picks up new models via app/db/models/__init__.py
```

**Backend tests (pytest + httpx, hits the real `company_postgres` DB — no mocking):**
```bash
cd backend
pytest                                  # all tests
pytest app/tests/test_product.py        # single domain
pytest app/tests/test_product.py::test_create_get_list_product   # single test
```
Tests use `httpx.AsyncClient` with `ASGITransport` against the real FastAPI `app` and the real async session from `app/db/base.py`. There is no test-DB isolation/transaction rollback — each test creates its own rows (usually with a UUID-suffixed unique name) and explicitly deletes them in a `finally`/cleanup helper. Tests require migrations to have been applied first (tables must exist).

**Frontend, local dev:**
```bash
cd frontend
npm install
npm run dev          # vite dev server, port 5173, proxies to VITE_API_URL (default http://localhost:8000)
npm run build         # tsc -b && vite build
npm run preview       # serves the production build, port 4173 (matches docker-compose)

```

## Architecture

### Backend: domain-module pattern

The backend is organized as independent **domain modules**, each touching exactly three layers under `backend/app/`:

```
db/models/<domain>.py     SQLAlchemy ORM models for that domain's tables
api/schemas/<domain>.py   Pydantic request/response schemas
api/routes/<domain>.py    APIRouter with the domain's full CRUD surface
```

Domains: `product`, `project`, `pipeline`, `backlog`, `task`, `agent`, `artifact`, `governance`, `demand` (the Inbox — see below), `prompt_commands`, plus `foundation`, `system_control`, `hindsight` (all three host-bridge proxy domains — no DB table of their own, see below) and `auth` (placeholder — see below).

Key conventions, binding for any new domain code (stated in docstrings across `db/base.py` and the model files — read one model file like `db/models/product.py` before adding to a domain):

- **UUID primary keys, Python-side default.** Always `mapped_column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)`. Never autoincrement ints or server-side `gen_random_uuid()` — IDs must exist before flush/commit.
- **`TimestampMixin`** (in `db/base.py`) gives every model `created_at`/`updated_at` for free — don't redeclare them.
- **Cross-domain foreign keys are string-form and lazy.** A domain never imports another domain's model module to declare an FK; it writes `ForeignKey("company.<table>.id")` as a plain string. This avoids import-order coupling between domain modules. All domain modules get imported together (and thus all FKs resolved) centrally in `app/db/models/__init__.py`, which Alembic's `env.py` also imports for autogenerate.
- **Polymorphic references use (entity_type, entity_id), not a FK** — e.g. `governance.Approval`/`AuditEvent` target many different table types and deliberately skip a real FK (see `db/models/governance.py` docstring).
- **Status/enum-like fields are plain `String` + a `CheckConstraint`**, not native Postgres ENUM types — keeps migrations simple, avoids `ALTER TYPE` churn. The allowed value tuple lives next to the model (e.g. `PRODUCT_VERSION_STATUSES` in `db/models/product.py`) and is re-validated at the route layer.
- **Business rules live at the API layer, not as DB constraints**, whenever they require a second statement or cross-row checks (e.g. "every product must have ≥1 version" — enforced in `create_product`/`delete_version` in `api/routes/product.py`, not a constraint). Route docstrings cite the specific SPEC.md §6 rule they implement — check there before changing CRUD behavior.
- **Routes own their full path.** Every `api/routes/<domain>.py` exports a module-level `router = APIRouter(prefix="/api/v1/<resource>", tags=[...])`; `app/main.py` only does `app.include_router(...)` and never adds prefixes itself.
- **Settings are centralized.** `app/core/config.py`'s `settings` object (pydantic-settings, loads repo-root `.env`) is the only place reading env vars — `db/base.py`, `core/security.py`, and `alembic/env.py` all import `settings` rather than touching `os.environ` directly.

### Backend: non-domain pieces

- **Login is protected by Google reCAPTCHA v2 (2026-09-08)** — `core/recaptcha.py`'s `verify_recaptcha` (mirrors darckware's `app/core/recaptcha.py`) is called from `api/routes/auth.py`'s `/api/v1/auth/token` before any credential check, using `settings.RECAPTCHA_SECRET_KEY` (`.env`). Fail-open when that's empty (dev/local keeps working with no key). It is now configured and enforced in production with a key pair scoped to `forgehub.darckware.net` (created 2026-09-08, separate from darckware's own key). Frontend: `LoginPage.tsx` renders the widget (`theme="dark"`, `react-google-recaptcha`) only when `VITE_RECAPTCHA_SITE_KEY` is set, baked in at image build time via `frontend/Dockerfile`'s `ARG`/`docker-compose.yml`'s `build.args` (sourced from root `.env`'s `RECAPTCHA_SITE_KEY`, itself not a secret). Rotate either key by regenerating it at the same reCAPTCHA admin console entry and redeploying (backend: restart is enough; frontend: rebuild, since Vite bakes the site key at build time).
- **FastAPI's own `/docs`, `/redoc` and `/openapi.json` are disabled by default (2026-09-08)** — `app/main.py` only passes real values for `docs_url`/`redoc_url`/`openapi_url` when `settings.ENVIRONMENT` (new, `core/config.py`, default `"production"`) is one of `development`/`dev`/`homolog`/`homologacao`/`staging`; any other value, including unset, disables all three. This closed a real public exposure: `forgehub.darckware.net` fronts the frontend container, not the backend, so the schema wasn't reachable through that domain, but `forgehub-backend`'s port 8000 is bound on the host's public interface (`0.0.0.0:8000`, see `docker-compose.yml`) and was serving the live OpenAPI schema (every `/api/v1/*` route's shape) to anyone who reached it directly. `frontend/nginx.conf` also gained an explicit `location ~ ^/(docs|redoc|openapi\.json)$ { return 404; }` so those three well-known probe paths read as closed (404) rather than falling through to the SPA's catch-all (`try_files $uri /index.html`, a 200) on the public domain. To re-enable docs for local/homolog work, set `ENVIRONMENT=development` (or `homolog`) in `.env`.
- **`auth.py` is an explicit placeholder.** It checks credentials against a single hardcoded dev user from `settings.DEV_USER_USERNAME`/`DEV_USER_PASSWORD` — there is no real Users/Auth domain yet (out of scope per PRD/SPEC at this stage). Its docstring asks that a future real implementation keep the same contract (`POST /api/v1/auth/token`, `OAuth2PasswordRequestForm` in, `{access_token, token_type}` out).
- **`foundation.py` is mostly a filesystem-only router**, with one deliberate exception. It reads from filesystem mounts (`/vault/Agents`, `/profiles`) to expose Hermes Foundation agent metadata (SOUL.md, sub-agents, skills, MEMORY.md) over HTTP. It also owns the per-profile `hermes cron` job stores (`<profile>/cron/jobs.json`): the list endpoint reports unparsable stores via `store_errors` (a corrupted store silently stops every cron in that profile — never swallow that) and refreshes a `.jobs.json.good` recovery snapshot on each clean read. SKILL.md read/write for the Skills page lives here too (`/foundation/skills/{name}/content`). Its **`/scripts` endpoint is the one place this router touches the database**: `_audit_check_script_refs` queries the `audit` domain's `audit_checks` table (enabled checks only) so a script invoked solely by an Auditor check's command — no corresponding cron job — isn't wrongly reported as `"unused"` (2026-07-09); `_foundation_registry_script_names` extends the same idea to the `foundation_scripts` table (the Foundation page's Scripts registry, `foundation_script.py`'s own domain) so a script documented by a Hermes/Foundation governance doc (`doc_path` set, or hand-registered) also counts as referenced even with no cron job, no Auditor check, and no systemd/ad hoc trigger ForgeHub can see (2026-07-11 — see `docs/SCRIPTS_AND_CRONS.md`'s §3 for the incident: `worker.sh`/`kanboard-cleanup.sh`/`send_demand.sh`/`health_check.sh` kept showing as "Old/unused scripts" in System Control's Cleanup card despite being registered there). `_list_scripts` reads every profile's `scripts/` dir off the event loop via `asyncio.to_thread` and returns the raw file content alongside the list so `system_control.py`'s cleanup-scan can reuse it (hashing for duplicates) instead of re-reading every script from disk a second time; script identity there is keyed by `(profile, filename)`, not filename alone, since two profiles can each have a same-named script.
- **`demand.py` is the Inbox** — ForgeHub's "console de desenvolvimento" intake: any agent (via the bridge-token `/demands/submit`) or the logged-in user (via the JWT `/demands`, backing both the chat's `/demanda` command and the Inbox page's "Nova nota" compose dialog) files a note here, which a human then reads and converts. `core/conversions.py`'s `CONVERT_TARGETS` has 7 targets: `task`/`doc`/`artifact`/`knowledge_base` (the original four) plus `planning_item`, `project_doc`, and `quick_task` (project-scoped — create a planning item, a project-linked doc, or a planning item + task together in one call, since a task can never exist without a planning item per the core traceability invariant). Every new demand also inserts a `Notification(source="system")` so arrivals surface in the existing bell, and `POST /demands/{id}/notify-telegram` forwards a demand through the host-bridge's cross-channel messaging proxy (see below). `demand_attachments` stores uploaded files under the same `/docs` mount `docs.py` writes to.
- **`factory.py` is an aggregation-only domain** (no table of its own, like `foundation.py`/`system_control.py`, except it reads the DB instead of the host bridge). `GET /api/v1/factory/cockpit` returns a **Product → Project tree** (not a flat project list) and reduces the product/system_scope/backlog/task domains to the five-phase state the cockpit renders. The joins are outer and Product is the root on purpose: this screen replaced the Products/Projects pages in the sidebar, so a product with no version — or a version with no project — must still appear, otherwise it becomes unreachable rather than merely unlisted. Writes are *not* here: the Cockpit's "New product"/"New project" call `POST /products` and `POST /projects` directly, so each domain keeps its own business rules (e.g. a product is never persisted without a version, rule 6.1.3). Each source domain's status vocabulary is mapped to a four-state traffic light (`approved`/`in_progress`/`pending`/`blocked`) through explicit dicts, never heuristics — an unknown status degrades to `pending` rather than being coerced into a green, and an empty set of tasks is `pending`, not "approved because 0 of 0 are done". It is read-only by design: approving a phase stays with the domain that owns the gate, so the cockpit can't become a back door around the approval gates.
- **Every task is executed through the Messages channel** (Marcelo's decision, 2026-07-26). `POST /api/v1/tasks/{id}/dispatch` does *not* introduce a second executor: it builds the linked message (`AgentDemand` with `origin_type="task"`, `origin_id=task.id` — the same link `update_task_execution` already stamps back) and hands it to `demand.py`'s `_execute_dispatch`, which remains the only path to the host-bridge's governed runner (`core/agent_runs.py`). Reusing that path is what makes the run appear in Messages like any other, the agent's reply come back as a linked item, and the existing `run_dispatch_completion_pass` reconciliation cover tasks with no new code. The legacy `/api/v1/orchestration/tasks/{id}/dispatch` stays retired (410, per `ER-RUN-01`).
- **`dispatch_task` gates on `TaskDependency` before it even resolves a target agent (Pacote 3, 2026-08-01)** — a task with a predecessor not yet `done`/`deployed` gets a `409` with the blocking list (`{task_id, task_number, title, status}` per predecessor) instead of being dispatched. Ported straight from `execution.py`'s `_preflight` (the separate, retired-for-direct-dispatch Execution Wave/Work Package pipeline already had this check) rather than reinvented — Messages stays the single executor, it just gained the same gate. `ProjectTask.plan_brief` (`Text`, nullable) is new too: the HOW/approach/acceptance-criteria, distinct from `description` (the WHAT); never required, included in the dispatch message body when set. Separately, `:authorize-delivery-planning` (`system_scope.py`) now auto-wires responsibility: a `ProjectSpec.responsible_agent_id` creates a `ProjectAgentMembership` on the new Project (`role` from `ROLE_BY_SOLUTION_TYPE` — `developer` for web_app/mobile_app/api_service, `data_engineer` for database, `release_manager` for deploy — PM-lifecycle vocabulary, not per-layer, so `developer` doesn't distinguish frontend from backend) and a `TaskAssignment` (with `membership_id` set, the field `TaskAssignment`'s own docstring says automated dispatch requires but nothing enforced before this) on every task it creates in that Project's scope. Also: an `experience`/`screen`|`route` element's `spec_snapshot.target_platforms` (`["web"]`/`["mobile"]`/both-if-absent) now disambiguates which of `web_app`/`mobile_app` a screen's task lands in — untagged elements still go to both (pre-Pacote-3 behavior unchanged), so this is opt-in, not a breaking change to existing Concepts.
- **Approving an `Approval(entity_type="project_task")` auto-dispatches it via Messages (Pacote 4, 2026-08-01)** — `governance.py`'s `_decide_approval`, after committing the decision, calls a new `_dispatch_task_by_id` (extracted from `dispatch_task` in `task.py` so both the route and this hook share the exact same dispatch logic — no HTTP self-call, no reimplementation). A dispatch failure (unfinished dependency, no active assignment, host-bridge down) does **not** undo the already-committed approval — it degrades to a `Notification` ("dispatch it manually once resolved"), same best-effort spirit as the rest of the dispatch machinery. `ApprovalForm.tsx` already had an `entity_type="project_task"` picker built in before this — it was just never wired to any effect. Also fixed in the same pass: `dispatch_task`'s `AuditEvent(..., description=...)` was a **latent bug since Pacote 3** — the model has `actor`(required)/`payload`, not `description`, so every *successful* dispatch was raising after the real host-bridge call had already fired (no commit yet, "Caller commits"), silently losing the DB record of a dispatch that had actually happened. Fixed to `actor="forgehub", payload={"description": ...}`; no test had exercised the success path until this pass added one (mocking `dispatch_agent_run`, same pattern as `test_demand_backlog_dispatch.py`).
- **Publishing a `ProductVersion` is a dedicated action, `POST /api/v1/products/versions/{id}:publish` (Pacote 4, 2026-08-01), not a `PUT status=published`** — idempotent if already published; otherwise blocks (409 + the blocking list, same UX as the Pacote 3 dependency gate) if any Project under that version has a `ProjectTask` outside `done|deployed|cancelled`. Deliberately never force-completes work to unblock itself (Marcelo: publishing shouldn't invent completion that didn't happen). A new `_assert_version_editable(db, project_id)` helper (`system_scope.py`) locks further mutation of Escopo (`add_project_scope_item`)/Telas (`create_screen`/`update_screen`/`remove_screen`/`write_screen_business_rule`/`derive_database`) and Planejamento (`backlog.py`'s `update_planning_item`) once the Project's version is published — **deliberately not applied to Concept/System Blueprint**, since those are Product-level, not tied to one version (a Product can keep revising its Concept for the *next* version after the current one publishes); locking them would have been wrong, not just incomplete.
- **`factory.py` also reports agent execution telemetry and per-project cost (Pacote 5, 2026-08-01)** — `GET /api/v1/factory/agent-telemetry` aggregates `TaskExecution`/`TaskAssignment`/`AgentDemand` per agent (there is no ORM relationship between `TaskExecution` and `Agent`, only `assignment_id`→`TaskAssignment.agent_id`, both nullable, so every join is explicit). Success/failure buckets reuse `EXECUTION_TERMINAL_STATUSES` (`{"verified","completed"}`, already defined in `schemas/task.py`) rather than inventing a second vocabulary; `"failed"` counts as failure, everything else (`pending`/`running`/`blocked`/`paused`/`reconciling`/`recovering`/`retried`) is "other/in progress" — `retried` isn't special-cased since Pacote 3b (retry automation) doesn't exist yet. An agent with no execution and no `AgentDemand` dispatch is simply absent from the response, not a fabricated zero row. `GET /api/v1/factory/cockpit`'s `ProjectCockpitRow` gained `total_cost` (sum of `TaskExecution.actual_cost` reached the same way phase 4 already reaches tasks: task → planning item → project, reusing the same `planning_to_project` map). Frontend: `useCockpit()`/`cockpitSchema` (`useFactory.ts`) had existed since Pacote 1's cockpit endpoint but were **never wired to any screen** — the Cockpit page recomputed its 5-phase strip from raw `useProducts`/`useProjects`/`usePlanningItems`/`useTasks` instead. `pages/cockpit/index.tsx` gained a "Telemetria" tab (finally consuming `useCockpit()` for a per-project phase+cost breakdown, plus the new `useAgentTelemetry()` via `AgentTelemetryPanel.tsx`) and lost its "Pipeline" tab's mock agent-status card (fictitious `#Hephaestus`/`#Scriba` data); the Execution Waves mock card was left untouched — a separate, not-yet-real concept, out of this package's scope. No charting library was added — `AgentTelemetryPanel.tsx` follows `DemandsStatsPanel.tsx`'s established hand-rolled SVG+Tailwind pattern (`StatTile`/`BarRow`/14-day sparkline, each panel keeping its own small unexported copies rather than sharing a utility).
- **"Backlog" no Messages virou "Incubação" (`incubation`), e ganhou três invariantes de banco (2026-08-13, Marcelo: "Backlog de tarefas de projeto é planejamento futuro e backlog de messages é outro conceito").** O produto já gasta a palavra "backlog" no planejamento de versão (o domínio `backlog`: `PlanningItem`/`FeatureRequest`/`BugReport`), e uma palavra para dois conceitos não relacionados convida semântica de sprint/estimativa para um espaço que é de amadurecer uma ideia. `incubation` nomeia o *estado*, não o conteúdo, e era o único candidato livre no código (`triage` pertence justamente àquele domínio de planejamento — `triage_decisions`; `draft` ao rascunho do compose; `nota` a um Tipo aposentado em 2026-07-26). `DEMAND_ORIGIN_TYPES = ("task", "incubation")`, migration `c4e81a90f3d7` (backfill antes de apertar o CHECK, mesmo formato da `f1b3d5a7c9e2`). O conceito: um pensamento estacionado até o **agente dono** decidir recebê-lo (vira Task) ou descartá-lo com motivo — nunca dispara sozinho, nunca carrega `origin_id`. **Os três invariantes são `CheckConstraint` no banco, não regra de rota** — exceção deliberada à convenção "business rules live at the API layer" (`db/base.py`), porque uma regra que só vale quando o chamador lembra dela é exatamente a falha sendo eliminada: (1) toda incubação tem dono (`incubation_owner_id`, resolvido `target_agent_id` → `from_agent_id`; sem nenhum dos dois a escrita é **recusada com 400**, mudança de comportamento em relação ao item órfão que antes era aceito); (2) todo item tem estado explícito (`incubation_state`: `incubating` → `decision_pending` → `promoted`|`dropped`) e um descarte sempre tem `drop_reason` — sumir da vista não é desfecho, e descarte é `status="archived"`, nunca DELETE; (3) todo item tem prazo (`matures_at`, default +3 dias). Um `event.listens_for(before_insert/before_update)` em `db/models/demand.py` deriva o que dá para inferir (dono pela mesma cascata, estado, prazo) para que os invariantes não virem imposto sobre todo escritor — ele **não inventa** dono quando não há nenhum, esse caso ainda falha. Cuidado ao mexer nele: `origin_type` tem `server_default`, então no flush o objeto Python ainda tem `None` — ler `None` como "não é incubação" limparia justamente os campos que a linha vai exigir. **O agente decide pelo MCP**: `list_my_incubation()`, `receive_incubation(number)`, `drop_incubation(number, reason)` (rotas `POST /demands/{id}/incubation:receive|drop`, bridge-token, só o dono — outro agente recebe 403, decidir duas vezes 409). Sem essas três ferramentas o ciclo não fecha: o agente recebe a decisão e não tem como respondê-la. Detalhe completo: `FORGEHUB_MESSAGE.md` §Incubation.
- **Motor de maturação da Incubação (fase 2, 2026-08-13)** — `run_incubation_maturation_pass` (`demand.py`), em loop próprio de 5 min no `main.py` (`_incubation_maturation_poll_loop`, tarefa separada pelo mesmo motivo do `_dispatch_completion_poll_loop`: as duas falham independentemente, e uma queda do host-bridge não pode impedir decisões de serem entregues). É o que torna o invariante 3 real — sem ele `matures_at` é só uma coluna. Varre incubações `incubating` com prazo vencido e, para cada uma: estado vira `decision_pending`, **`agent_processed_at` é zerado** (o item volta para `GET /demands/pending`, a fila que os agentes já puxam do próprio cron) e uma `Notification(severity="warning")` é criada, deduplicada por `event_key`. A entrega reaproveita a fila de pull de propósito: despachar geraria um run inteiro só para fazer uma pergunta, e criar uma segunda mensagem produziria um item que também precisaria de dono e prazo — mais uma coisa para esquecer. Idempotente por estado, não por tempo: só linhas `incubating` são pegas e cada uma vira `decision_pending` na mesma transação, então uma decisão nunca é entregue duas vezes nem uma já decidida é reaberta. Efeito colateral esperado do lado do agente: um pensamento pode reaparecer em `check_agent_inbox()` — não é duplicata, é o prazo sendo cobrado.
- **Contingência de despacho: prazo, teto de concorrência, tentativas e reprocessamento (2026-08-13, Marcelo: "notificação de todas as falhas ao usuário, e prazo para retorno e adicionar um icone de reprocessamento das falhas").** Cinco modos de falha existiam e só um avisava alguém; o pior era invisível — um run que trava fica em `running` para sempre, nunca chega a estado terminal e por isso **nunca dispara o feedback**, que só ocorre em `completed`/`failed`. Quatro regras fecham isso: (1) todo despacho carrega `dispatch_deadline_at` = agora + `DISPATCH_TIMEOUT_MINUTES` (45 min, acima dos 1800s do host-bridge para não matar um run que ainda ia terminar, e aplicado aqui porque um bridge morto não aplica limite nenhum) — `run_dispatch_timeout_pass` varre e marca `failed`; (2) **toda** falha notifica, por um único `_fail_dispatch` usado por todos os caminhos, para não ser verdade em um e silenciosamente falso nos outros; (3) reprocessamento é **manual** (`POST /demands/{id}:reprocess`, ícone no grupo Falhas e no item) e limitado a `DISPATCH_MAX_ATTEMPTS` (3) — retry automático numa falha permanente queimaria ciclos a cada 30s e esconderia a causa, e `dispatch_attempts` **nunca** é zerado, senão o limite seria inalcançável por construção; (4) no máximo `MAX_CONCURRENT_DISPATCHES` (5, ajustável em Settings → System defaults, teto 20) em voo **e no máximo um por agente** (Marcelo: "para os processos não misturar" — cinco vagas caindo no mesmo agente iniciariam cinco sessões do mesmo CLI no mesmo perfil e working path, sobrepondo contextos). O teto conta o que **já está em voo**, não o que um passe vai enviar; um agente ocupado é **pulado**, não bloqueia a fila. Ordem: não é configurada — decorre do que a mensagem já é ao ser lançada (Tipo decide se entra na fila, `scheduled_at` decide a posição); reprocessar é um novo lançamento, então vai para o fim. Reprocessar **não despacha inline**: devolve à fila, então um reprocesso em massa continua respeitando o teto.
- **Retenção de 60 dias para mail terminal (2026-08-15, Marcelo: "as messages precisam ter um plano de limpeza podendo ficar até 60 dias")** — `run_demand_retention_sweep` (`demand.py`), poll a cada 6h (`_demand_retention_poll_loop`), arquiva (nunca apaga) toda mensagem `completed`/`failed` cujo `updated_at` passou de `DEMAND_RETENTION_DAYS` (60). Nunca toca Incoming/Outgoing/Running/Incubation, não importa a idade — só como terminou importa, não há gatilho por idade de criação. `updated_at` faz as vezes de "quando terminou" (não existe coluna dedicada; a escrita de `_finalize_dispatch`/`_fail_dispatch` é, à parte a entrega de feedback quase simultânea, a última naquela linha). Os botões manuais da barra (30d/15d/"Limpar tudo", `cleanupTargetIds` em `pages/demands/index.tsx`) ganharam o mesmo filtro — antes varriam a tabela inteira por idade sem olhar estado nenhum, o que apagou de vez uma leva de mensagens já arquivadas no mesmo dia (o "Clear all" não filtra por grupo, é literal). Cópia i18n dos diálogos de confirmação atualizada pra descrever o escopo real em vez de "todas as mensagens".
- **Feedback ao meio de comunicação (2026-08-13; opt-in Telegram confirmado em 2026-08-23)** — Messages executa tudo, mas o resultado ficava preso dentro do Messages. `AgentDemand.channel` + `channel_ref` registram **por onde o pedido chegou** e **o endereço concreto de retorno**; `core/feedback.py` entrega em estado terminal. Chamado "meio de comunicação", não "origem" (Marcelo: "Para não confudir a origem vamos falar meio de comunicação") — `origin_type` já significa o Tipo, e uma palavra para dois conceitos foi o erro que "backlog" cometeu. **Dois campos, não um**: saber que é "telegram" não basta, pois é necessário o `chat_id` da conversa que pediu. Além disso, retorno externo pelo Telegram é **opt-in pelo contexto da própria mensagem**: `channel="telegram"`/`channel_ref` sozinhos não autorizam envio; o assunto ou corpo precisa pedir explicitamente resposta/retorno/notificação pelo Telegram, usando o detector estreito `wants_telegram_reply`. Sem esse pedido, o resultado fica na notificação interna e `feedback_sent_at` é encerrado, evitando retry externo infinito por metadado antigo ou inválido. Quando solicitado, só dispara em `completed`/`failed` (Marcelo: "o feedback só é enviado quando for concluido ou erro da task"), e falha conta — inclusive a que nunca rodou, já que alguém esperando resposta que nunca virá é o pior desfecho. `channel="agent"` é **deliberadamente pulado**: `requires_response`/`reply_to_id` já roteia essa resposta, e entregar aqui duplicaria na caixa do agente. Idempotente por `feedback_sent_at`, que é coluna e não log justamente para tornar uma entrega perdida **encontrável** — terminal com carimbo nulo = feedback ainda devido, recuperado pela varredura de 2 min. Regra de responsabilidade acordada: **quem recebeu a demanda devolve** — agentes Hermes notificam direto; os externos (executores puros) pedem ao orquestrador que notifique.
- **`AgentDemand.working_path` (2026-08-13)** — o cwd em que o run do agente destinatário começa, por mensagem; `NULL` cai para `settings.AGENT_RUNTIME_PATHS[runtime_type]`, depois `/root`. - **A Tipo=Task message with no target agent is silently downgraded to Backlog, never rejected** (2026-07-27, Marcelo: "toda task chegando em Incoming precisa ser executada pelo seu agente" — then, refining the first cut which errored instead — "não seria melhor sem agente ficar no backlog... para não ser executado"). `demand.py`'s `_reconcile_task_origin` does the downgrade (origin_type -> "backlog", origin_id cleared — Backlog is a classification and structurally never carries a link), checked against the *final* merged state on both `create_demand_and_notify` and `update_demand` — so it also catches the reading pane's "Promover a Task" button, which flips `origin_type` through the same PATCH as any other edit, and clearing To on an already-Task message. Paired with an auto-schedule for the Task-with-target case: never dispatched and never had `scheduled_at` set gets it defaulted to now. Since 2026-08-23, the commit calls `wake_scheduled_dispatch`, so the single dispatch worker relê o banco e inicia o run imediatamente; o sweep de 30s ficou apenas como contingência para restart, escrita externa, agenda futura ou sinal perdido. This closes the gap for every writer of the endpoint, not just the compose form. Fires once: only when `scheduled_at IS NULL`, so a later unrelated edit on an already-scheduled or already-dispatched Task never re-triggers it. A completed Task is not moved out of Incoming — it stays there under its agent, `task_execution_at` stamped, and also shows up in the cross-cutting Finalizado view (grouped by `target_agent_id` since 2026-07-27); dual placement is intentional, not a bug. Since 2026-07-28 the same function also defaults a wholly-omitted `origin_type` to `"backlog"` (`origin_type IS NULL` is now a genuine `if` branch, not the fallthrough) — Tipo is `NOT NULL` at the DB level, see the bullet below.
- **Tipo (`origin_type`) is mandatory, exactly two values — the old third value, "demand", is retired (2026-07-28, Marcelo: "no type só sistem dois tipo task ou backlog e o campo é obrigatório... não temos resposta automática. somente processamento").** `DEMAND_ORIGIN_TYPES = ("task", "backlog")`, column `NOT NULL` with `server_default='backlog'` (same reasoning as `requires_response`'s server_default — a raw insert that doesn't know about the column needs the DB to supply a value). What "demand" used to encode (an auto-generated reply, threaded via `origin_id` to the message it answered) is now two separate columns on `AgentDemand`: **`dispatch_result`** (`Text`, nullable) — the agent's raw output, written onto the *same* dispatched message by `_finalize_dispatch` regardless of `requires_response`, "processamento" with no new row — and **`reply_to_id`** (a real self-referential FK, unlike `origin_id`'s deliberate polymorphism) — set only when the original had `requires_response=true`, pointing back at the message a return message answers. `_finalize_dispatch` (`demand.py`) now: always stamps `dispatch_result`; only when `requires_response and from_agent_id is not None` also creates a second `AgentDemand` (`from_agent_id`/`target_agent_id` swapped to executor→sender, `origin_type="task"`, `requires_response=False` to avoid a reply loop, `dispatch_status="completed"`/`task_execution_at` set directly since it's already-done work that's never itself dispatched — needed so it reads as *arrived* under the letter model's gate on creation, not after some later poll). This reverts 2026-07-27's "every reply routes back regardless of `requires_response`" from a routing-only gate to a creation gate, per Marcelo: "preciso gerar... uma mensagem de retorno quando solicitado pelo agente... e o padrão é não". Migration: `f1b3d5a7c9e2_demand_origin_type_mandatory_reply_to.py` (backfills any existing `NULL`/`"demand"` row to `"backlog"` first).

Isso é regra").** `_reconcile_task_origin` now downgrades Task → Backlog when *either* `target_agent_id` or `from_agent_id` is `None`, extending the 2026-07-27 target-only check — a Task addressed to someone but from no registered agent has nobody for `dispatch_result`/the return message to belong to. `_assert_dispatchable`'s Backlog-needs-sender guard is unaffected (a Task can never reach it with `from_agent_id=None` any more, so its old "deliberately not extended to task" reasoning updated to explain why instead). - **`agent.py` also owns the per-agent profile Markdown files** (`GET/PUT /api/v1/agents/{id}/profile-files[/{filename}]`, resolution in `core/agent_profile_files.py`). Every agent is defined by the same file set — `SOUL.md`, `IDENTITY.md`, `USER.md`, `TOOLS.md`, `AGENTS.md`, `FOUNDATION_LINK.md`, `HEARTBEAT.md`, `MEMORY.md`, `CONTINUITY.md`, plus a runtime extra (`CLAUDE.md` for Claude Code) and the optional `<PROFILE>_SUBAGENTS.md` — but not the same *directory*: Hermes profiles live at `/root/.hermes/profiles/<slug>`, while the four external CLI runtimes live at `/root/.claude` (Porthus), `/root/.codex` (Aramis), `/root/.gemini/config` (Dartan) and `/root/.openclaw/workspace` (Vector). Those are conventions; `agents.home_path` overrides them per agent. This is why it is *not* in `foundation.py`: that router's `/profiles/{profile}/files/{filename}` walks the `/profiles` mount and structurally cannot see any agent that isn't a Hermes profile (it stays in place for its existing callers). Paths are stored host-canonical and resolved by trying the host path, then the named bind mount, then `/host-root` — `filename` comes from a URL segment, so it is always checked against the per-agent allow-list and required to resolve inside the home directory.
- **`agent.py` also owns each agent's MCP servers** (`GET /api/v1/agents/mcp-servers` for the whole roster, `GET|PUT|DELETE /api/v1/agents/{id}/mcp-servers[/{name}]`, formats in `core/agent_mcp.py`; UI: the **MCP Servers** page at `/mcp` and a card on the agent page). Every runtime keeps its MCP config in its own file, format and key — Hermes `<home>/config.yaml` (`mcp_servers`), Claude Code `~/.claude.json` (`mcpServers`), Codex `~/.codex/config.toml` (`[mcp_servers.*]`), agy `~/.gemini/config/mcp_config.json` (`mcpServers`), OpenClaw `~/.openclaw/openclaw.json` (`mcp.servers`) — and two of them sit *beside* the home directory rather than inside it, which is why the mapping carries an `in_parent` flag rather than reusing `home_path` directly. **There is no ForgeHub table behind this**: a copy would drift the moment someone ran `claude mcp add` in a terminal, so these routes read and edit the runtime's own file, which is what the runtime actually loads. Writes to the two commented formats (YAML, TOML) are line-surgical — a `yaml.safe_dump` round-trip of a live profile config would flatten its comments and key order for the sake of one entry. Only `hermes`/`codex`/`openclaw` have an enable/disable flag; for Claude Code and agy, removal is the only "off", and the UI hides the toggle rather than faking it with a delete.
- **Two syncs, deliberately different sources.** `POST /api/v1/agents/sync/hermes-foundation` reads the canonical Foundation *docs* (`core/hermes_sync.py`) — authority for who an agent is: layer, mission, role, sub-agents, skills. `POST /api/v1/agents/sync/runtimes` (`core/agent_runtime_sync.py`, the button on the MCP Servers page) reads the *host* — authority for what an agent runs: a `/root/.hermes/profiles/<slug>` directory means `hermes`, an external runtime home means that runtime. The doc sync structurally cannot answer the second question, which is exactly how Kairos stayed registered with `runtime_type` NULL while its profile directory, gateway unit and MCP config all existed — and every MCP screen reported it as an agent no runtime would ever load a server for. The runtime sync only ever *fills in* a missing value: a registered runtime decides the real command line in `core/agent_runs.py`, so a registry that contradicts the disk is reported, never silently "corrected", and a profile directory no agent claims is listed rather than turned into a row.
- **`agent.py` also reports per-agent Telegram channel health** (`GET /api/v1/agents/telegram-status`, logic in `core/agent_telegram.py`). Two signals kept separate because they fail separately: *installed* (`TELEGRAM_BOT_TOKEN` + `TELEGRAM_HOME_CHANNEL` in the agent's own profile `.env` — the token is reduced to a boolean before it leaves the module and is never in a response) and *running* (`hermes-gateway-<profile>.service` active, read via the host-bridge `/v1/exec` in one call for the whole roster). Installed-but-not-running is its own state: that daemon long-polls Telegram, so messages silently go nowhere. When the bridge is unreachable, `running` stays `None` and the status degrades to `unknown` — never to a failure state. Only `runtime_type == "hermes"` agents have a gateway unit; the external runtimes have a `profile_slug` too (their Inbox addressing key, not a `/root/.hermes/profiles` directory), so keying the unit name off the slug alone wrongly reports a non-existent unit as down.

Comparing a freshly-read `ai_router.agents.api_key` against the stored encrypted value can't compare ciphertext directly (Fernet is nondeterministic, a fresh IV every call), so both sync paths decrypt-and-compare (`_forgerouter_key_unchanged` in `api/routes/agent.py`) before deciding whether a write is actually needed — re-running either sync when nothing changed reports `updated: 0`, not a false positive on every call.
- **`server.py` (the SSH inventory) now vaults the key itself, not just its path (2026-08-14, Marcelo: "seria melhor criptografar a chave no banco de dados para não perder").** `Server.private_key_encrypted` holds the identity file Fernet-encrypted (`core/secrets.py`, the same boundary as `Agent.forgerouter_api_key_encrypted`); no endpoint ever returns it, `ServerOut` exposes only the boolean `private_key_stored`. Four admin-only routes make the round trip — `POST /{id}/key:backup` (read the host file through the bridge, store encrypted), `PUT /{id}/key` (vault a pasted key, for material this host doesn't have), `POST /{id}/key:restore` (write it back at `ssh_key_path`, 0600), `DELETE /{id}/key` — backed on the host by `/v1/servers/read-private-key` and `/v1/servers/write-private-key`. Three deliberate constraints: the bridge validates every path against `PRIVATE_KEY_ROOTS` *after* `realpath` (the path arrives in a request body, and `/root/agents/aegis` is a symlink, so a prefix check on the raw string proves nothing); a restore **refuses to overwrite** an existing file (409) since restoring is for a key that is *missing*, and silently replacing a working identity is a worse failure than reporting the conflict; and nothing is automatic — no backup on save, no restore on a failed connection, because a key silently reappearing on disk from a stale DB copy would be its own surprise. ### Frontend: per-domain page + hook pairing

Each backend domain has a matching `frontend/src/pages/<domain>/` (typically `index.tsx` list view, `[id].tsx` detail view, `<Domain>Form.tsx`) and a `frontend/src/hooks/use<Domain>.ts` (TanStack Query hooks). Pages whose main table should scroll internally (tools, skills, notifications, database, workspace) are "full-bleed": listed in `AppLayout.tsx`'s `isFullBleed` so `<main>` gets a definite `h-screen` height — without it the `flex-1 min-h-0 → overflow-auto` chain never binds and the table overflows the viewport with no scrollbar. `src/lib/api.ts` is the single fetch wrapper everything goes through — domain hooks call `apiClient.get/post/put/patch/delete` with the exact `/api/v1/<resource>` path; never hardcode `BASE_URL` or add path segments elsewhere. `BASE_URL` comes from `VITE_API_URL` (defaults to `http://localhost:8000`).

`src/components/ui/` holds shadcn/ui primitives (button, card, input, select, table, etc.) — extend this set via the shadcn CLI/pattern rather than hand-rolling alternatives.

**Coding standard: adopting the org's canonical `05-FRONTEND-ARCHITECTURE-AND-CODING-STANDARD.md` incrementally (2026-08-07, Marcelo: "precisa seguir padrão de desenvolvimento MVC no código... e orientação a objeto... precisamos adotar padrão de desenvolvimento" — pointed at the existing organizational standard rather than an invented convention; full doc at `/root/.hermes/knowledge_base/marcelo/stack/05-FRONTEND-ARCHITECTURE-AND-CODING-STANDARD.md`, methodology overview at sibling `03-SOFTWARE-DEVELOPMENT-METHODOLOGY-SPEC.md`).** That doc's target architecture is Feature-Sliced Design (`app → pages → widgets → features → entities → shared`, its §6-7) — **ForgeHub's actual frontend does not use those layers** (it's the flatter `pages/<domain>/` + `hooks/use<Domain>.ts` pairing described earlier in this section) and a full layer migration is out of scope for now; don't restructure directories to match §6-7 without an explicit decision to do so. What *is* being adopted now, gradually and one screen at a time ("de vagar por tela" — not a big-bang rewrite, don't retrofit every existing component in one pass) is the standard's component/state-layer split. **Track progress in `docs/architecture/FRONTEND_VIEWMODEL_MIGRATION_PLAN.md`** — a living checklist of every page/component, waved by priority; tick a screen's box in the same change that converts it (don't batch-update from memory later, per Marcelo: "nesse controle você tem que ir baixando automaticamente quando formos fazendo as correções nas telas"):
- **ViewModel Hooks (§21)** — when a screen/component has async state, a confirmation step, or coordination between fields (more than a couple of plain `useState`s), pull that state and the functions that mutate it into a `use<Thing>ViewModel` hook in `frontend/src/hooks/`, returning a `<Thing>ViewModel` interface with an explicit `status` state machine (`"idle" | "submitting" | "error"`, extended with `"loading"/"ready"/"confirming"/"success"` per the doc's own worked example when a screen actually has those steps) rather than a loose `boolean` per concern. The component becomes close to a pure render of that hook's return value — this is React's own idiom for the Model+Controller/View split the standard calls for, not a literal class (a mutable class instance would still need every field wrapped in `useState` to trigger re-renders, paying for the same encapsulation twice). Reference pair: `frontend/src/hooks/useImprovePromptViewModel.ts` + `frontend/src/components/chat/ImprovePromptDialog.tsx` — read the hook's own docstring before adding another one, it explains which parts of the doc's fuller example this dialog's simpler one-step flow deliberately doesn't need.
- **CRUD UX (§48 "Loading, empty e error states", and Marcelo: "os padrão de desenvolvimento inclui também uma tela de confirmação de exclusão, botões de animação para indicar a ação: gravar, editar, consultar e excluir... validação de campos do formulário")** — three of these are already the codebase's widespread de facto standard (keep following them deliberately, not by accident): destructive actions go through `src/components/ui/confirm-dialog.tsx`'s `ConfirmDialog` (`variant="destructive"`, `icon="trash"` by default — ~70 call sites already), never straight off a click; every button bound to a mutation shows `disabled={mutation.isPending}` plus a small `<Loader2 className="... animate-spin" />` (~60 files already do this — `ConfirmDialog`'s own `loading` prop and `ImprovePromptDialog`'s Rewrite button both use it) rather than a silent click while a request is in flight; forms validate with React Hook Form + `zodResolver` (14+ files already) off a Zod schema colocated with the domain's `use<Domain>.ts` hook when one exists (e.g. `taskCreateSchema` in `useTask.ts`) or inline in the form otherwise, never hand-rolled `if`-chains. The doc's fuller §48 state matrix (`Loading/Empty/Partial/Error/Offline/Permission denied/Not found/Success`, with dedicated `*Skeleton`/`ErrorState`/`NotFoundState` components) is **not** yet how most ForgeHub screens are built — most just gate on `query.isLoading`/`isError` inline — so treat the full matrix as the target for screens you touch going forward, not a claim about current state.

**The Messages sidebar's Incoming/Outgoing are gated to "still moving," each message in exactly one lifecycle group at a time ("the letter model", 2026-07-27, narrowed 2026-07-28)** — `isIncomingItem`/`isOutboxItem` (moved to `frontend/src/hooks/useDemands.ts` 2026-07-28 so they're shared with `Sidebar.tsx`, not just `pages/demands/index.tsx`): `isIncomingItem` requires `dispatch_status` non-`NULL` *and* not `dispatched`/`running`/`completed`/`failed` (Marcelo: "as message no Incoming em processamento tem que serem movidas para Running, fim do processamento, deu erro vai para Failed, senão vai para Completed"); `isOutboxItem` gained the same terminal-state exclusion (Marcelo: "executou move para completed, não fica tendo da Outgoing"). Net effect: a message now leaves Incoming/Outgoing the instant it starts dispatching, living only in Running, then only in Completed/Failed — the earlier "dual placement is intentional" note (a completed item staying visible in Incoming/Outgoing forever) no longer holds; each of Incoming/Outgoing/Running/Failed/Completed is mutually exclusive. Neither self-addressed items (`target_agent_id === from_agent_id`) nor System (`NO_AGENT_ID`) are affected by this narrowing beyond what the original 2026-07-27 gating already did. **Frontend display only** — the backend contract (`/submit`, `/for-agent`, dispatch, the MCP tools) is completely unchanged; `GET /for-agent` still returns every message regardless of dispatch state, exactly as `FORGEHUB_MESSAGE.md` documents for agent callers. `AgentCommsGraph`'s (Overview tab) `received` per-node tally deliberately did **not** follow this narrowing (would collapse to ~0 for every real dispatch, since nothing occupies the `pending` window Incoming was narrowed to) — it still mirrors only the original 2026-07-27 rule. All three "how many arrived" badges (Sidebar nav, the Messages page's own header pill, and the Incoming tree's own root badge) now read one shared `computeInboxTotalCount(demands)` (2026-07-28, Marcelo: "os todas tem que obedecer o total do grupo de entrada... tem que haver sync") — the header/sidebar pass the *unfiltered* `useDemands()` result so an active search doesn't shrink just one of the three, while the tree's own root badge passes the search-filtered `visible` list so it matches what the folder actually shows when expanded.

**The mutual-exclusivity invariant above regressed for one day and was reverted (2026-08-14 → 2026-08-15).** A same-day commit (`c3bbc21`, "Workspace: expand agent communication and prompt tooling") changed `isIncomingItem` to also match any generated return (`reply_to_id != null`) regardless of `dispatch_status`, and excluded those same rows from `isCompletedItem` (`pages/demands/index.tsx`) — the intent read as "a reply is delivered mail, show it arriving in Incoming." But a generated return is created already-terminal (`dispatch_status="completed"`, set directly by `_finalize_dispatch`, see the `origin_type` bullet above) — it never passes through `pending`/`dispatched`/`running`, so there was no later event left to move it back out of Incoming. Every reply piled up in Incoming permanently, only escapable by manual archive; a same-agent smoke-test batch alone produced 13 stuck rows. Both functions (and the `useDemands.test.ts` case rewritten for the regressed rule) were reverted to the state this section describes. If a reply ever needs its own visible "arrived" moment in Incoming, it needs a real exit event (e.g., flip out on read/archive) paired with the entry, not a rule that adds it to Incoming with no matching removal.

**Canonical rule settled 2026-08-15 (Marcelo, working through the model live): self-addressed work is Incoming, not Outgoing; "pending" is formally retired; every row has an owner, none are anonymous.** Three findings from the same audit, all fixed together:
- **Self-addressed is Incoming, not Outgoing** ("se o próprio agente que vai executar então ele não tem saída e sim uma entrada"). `To` left blank on submit already resolves to `From` (`DemandFormPanel.tsx`'s `effectiveTargetAgentId`), so a self-addressed row (`target_agent_id === from_agent_id`, both set) is work the sender addressed to itself — from that agent's own point of view that's mail that arrived, not mail it sent onward. `isIncomingItem` now requires `target_agent_id === from_agent_id` instead of excluding it; `isOutboxItem` now excludes it (a `selfDirected` guard, careful not to trip on the human-composed-Task case where both are `null`).
- **`"pending"` retired from `DEMAND_DISPATCH_STATUSES`, DB `CHECK` tightened (migration `60bb40510cb4`)**, not just left as documented-but-dead — it never had a writer (dispatch goes `NULL` → `dispatched` directly, see `run_scheduled_dispatch_pass`), so "the momentary pending window" the Foundation doc described was never real, only aspirational. With self-addressed now covering the "queued, not yet started" concept, dropping the value costs nothing and removes a state nobody could ever query for successfully.
- **"não existe anônima"** — an item with no `target_agent_id` is not ownerless by default: an Incubation row with no target yet still has `incubation_owner_id` (falls back to `from_agent_id`, `CHECK`-enforced non-null at the DB). `computeInboxTotalCount` and the Incoming tree's System/`NO_AGENT_ID` bucket were counting *any* no-target row as "System," double-counting an owned Incubation item into a badge it didn't belong to. Both now also require `!from_agent_id` — System means genuinely nobody's (a human-composed note with neither field set), not "no target field."
- **The MCP's CRUD gap closed**: `list_agent_messages`/`get_agent_message`/`check_agent_inbox` were already agent-parameterized (Create+Read, any agent) but Update/Delete only existed via the JWT-only human API. Two new bridge-token routes (`PATCH /demands/{id}/agent`, `POST /demands/{id}/agent-archive`, both scoped to the message's own sender — 403 for a stranger, same ownership line as `receive_incubation`/`drop_incubation`) plus matching MCP tools (`update_agent_message`, `archive_agent_message`). Building these surfaced a real pre-existing bug: `RequireAuthMiddleware` (`main.py`) had no carve-out for `/api/v1/demands/{id}/...` dynamic paths, so `receive_incubation`/`drop_incubation`/`reprocess_demand` — despite each doing their own `x_bridge_token` check — 401'd before ever reaching the route for a caller sending only `X-Bridge-Token` with no JWT, which is exactly what the MCP does. Unnoticed because every existing test of them also carried a JWT (`create_access_token`) alongside the bridge token. Fixed with a `demands_bridge_action` carve-out mirroring `channels_bridge_path`/`agents_bridge_path`; regression-tested in `test_demand_agent_crud.py` with a client that carries no `Authorization` header at all.

**Archived's uncategorized (no subfolder) items break down by agent too, keyed off sender not recipient (2026-07-28, Marcelo: "tem que agrupo por agentes igual ao Incoming")** — `InboxGroupTree.tsx` gained the same System+per-agent row rendering `AgentDirectionTree` already had (extracted `AgentRow` to a shared export in `AgentInboxTree.tsx` to reuse it), rendered above the existing user-created-subfolder tree, which is untouched (that axis stays thematic, not per-agent). Deliberately grouped by `from_agent_id`, not `target_agent_id` like Completed: a return message (from=executor, to=original sender) grouped by recipient put Atlas/Vector/etc.'s replies inside "Athos" while each row's bold name (`DemandListRow` shows `demand.from_agent`) still read "Atlas" — confusing on first look (Marcelo, catching it: "estão entrando outros agente no grupo do Athos"). `from_agent_id` keeps the group name and the row's own bold name in agreement. `SelectedFolder`'s `archived` variant gained an optional `agentId` alongside `groupId` to carry this new selection axis; `filtered`'s archived branch only enters agent-filtering when `groupId === null`, leaving subfolder navigation (`groupId` set) completely unaffected.

**Messages' compose/edit form: Tipo is now a plain two-option Select, and "Retorno" is back but agent-facing only (2026-07-28)** — the end state of an intermediate step earlier the same day that had removed "Retorno" from the form entirely, reverted once the "demand" Tipo redesign gave it real behavior again (see the two bullets above). `DemandFormPanel.tsx`: `OriginChoice = "task" | "backlog"` (no `"none"`, no `"demand"` — mandatory field, no read-only special case needed anymore since a return message is now Tipo=`task` like any other, editable normally). The "Retorno" Sim/Não `<Select>` is back in the form (`requiresResponse` state, shown when Tipo=Task), and a read-only "Resultado" `<Textarea>` renders below the body whenever `demand.dispatch_result` is set. `forgehub_messages_mcp.py`'s `send_agent_message` always sends `origin_type="task"`; its `reply_to_message_number` parameter is gone (no more manual reply-threading — `reply_to_id` is backend-generated only). `send_agent_message.sh` (the shared shell script, canonical for every Hermes agent) dropped `--origin-note` for the same reason and now also always sends `origin_type=task`. Full detail and the updated Tipo table: `FORGEHUB_MESSAGE.md`.

**Sidebar navigation** (`src/components/layout/Sidebar.tsx`) is data-driven from `src/components/layout/navSections.ts`'s `NAV_SECTIONS` — shared with `CommandPalette.tsx` (Cmd/Ctrl+K quick nav, filtered by the same `usePermission` checks) so the route list is never duplicated. Each top-level section groups by a single semantic criterion (e.g. "Agents & AI" is agent config only, "Operations" is infra/ops tooling, "Integrations" is external tool links) — when a new nav entry doesn't clearly fit an existing section, that's a signal to add a section rather than force it into a "misc" one. Section headers are independently collapsible (state in `localStorage`). The `/demands` route is labeled **"Mensagens"/"Messages"** in the sidebar (renamed from "Inbox" on 2026-07-26); the route and the `demand` domain keep their old names so existing links and integrations (`send_demand.sh`, `send_agent_message.sh`) don't break.

**Software Factory is the single development-cycle section** (2026-07-26). It replaced two overlapping groups: the old "Planning" section and a "Software Factory" section of static mockups under `/factory/*` (never committed, no API calls) that duplicated the same screens. The five development phases point at the real routes that already exist — `/conception`, `/system-map`, `/backlog`, `/tasks`, `/governance` — rather than at parallel screens. The section's order encodes the domain's granularity, which is worth knowing before adding to it:

- **Product** is durable. Conception and the System Map are recorded at product level (`product_concepts` and `system_blueprints` each hold a UNIQUE FK to `products`), so every project inherits phases 1–2 from its product.
- **Every evolution of a product becomes a Project**, which carries the description of what will be built and walks the five phases. `project_scopes`, `planning_items` and `project_tasks` are all project-scoped.
- The full chain is **Product → Project → Planning (groups) → Task**.

The Cockpit (`/cockpit`) is grouped by that same tree and **carries the registration of both**: create a product, create a project under it, and link into each one's detail page. Because of that, **Products and Projects left the sidebar** — a separate entry would only repeat the same path — but their routes stay in `navSections.ts` with `hiddenInSidebar: true`, since the Cockpit's own links point at them. Project Scope, Pipelines, Templates and Policies stay in `navSections.ts` with `hiddenInSidebar: true` — they belong inside a phase and have not been promoted to tabs there yet; dropping them entirely would also drop them from Cmd/Ctrl+K. **Artifacts left the navigation** (2026-07-26): per-phase detail is written as `.md` files instead (Docs and Conception's Documentation step). **Kanboard was discontinued and fully removed from ForgeHub** (2026-07-28, Marcelo: "preciso remover qualquer referência kanboard na aplicação. Porque foi descontinuado no sistema") — not just hidden from the sidebar as an earlier iteration had it: the `/kanboard` route/page, `kanboard_client.py`, the sync endpoints (`/tasks/{id}/sync-kanboard`, `/pull-kanboard`), and the `kanboard_project_id`/`kanboard_column_ids`/`kanboard_task_id` columns are all gone. Task execution was already native via the Messages channel (see below) and does not depend on this integration. **Task management and agent-to-agent communication are now handled entirely through ForgeHub's own MCP server (`forgehub`, see `backend/app/mcp/factory_server.py`), surfaced in the app by the Messages component/screen** (`demand.py`'s `AgentDemand`, `pages/demands/index.tsx`) — there is no external task tracker in the loop anymore.
